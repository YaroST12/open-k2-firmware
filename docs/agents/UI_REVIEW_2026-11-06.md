# K2 UI design review, 2026-11-06

Status: proposal only. No shipped UI code changed. The user approves before anything below is built.
Note (2026-11-08): this is a dated snapshot. `MenuList`, named throughout, no longer exists; its rows are the kit `RowList`
(`include/k2/ui/kit.hpp`), see `docs/UI_DESIGN.md`.
Base: main b097551 (Atkinson Hyperlegible Mono 4 bpp font, shared MenuList Tools/Settings UI).
Method: every page and stage rendered through the host path (`test_ui_capture`, `test_ui_mockup`, plus the scratch
harness `tests/test_ui_review_mockups.cpp`), then read against the standards below. No device was touched; no screenshots
from hardware. The after-mocks are drawn with the real fonts and the real primitives (`fill`, `gfx_text`, `draw_pill`,
`draw_footer`, `pill_width`) over the real before-screen, inside `ContentViewport`, so sizes and clipping are true; the
data in them is illustrative.

Sections: 1 scope and standards, 2 findings, 3 proposal per screen, 4 strip vocabulary, 5 implementation plan,
6 open questions, 7 coverage and limits.

## 1. Scope, posture, standards

Product posture (Cooper): the K2 is a transient tool at the bench (seconds per look) with a sovereign charger-test flow
(minutes, one task). Two reading distances (ISA-101 levels): Level 1 walk-by (Home: is power flowing, how much) and
Level 2 close-up (everything else). Constraints kept as given: four buttons and their semantics, the palette, Home's
walk-by role, the results grid, 240x240 with no framebuffer (row-streamed), content viewport 224x240 (240x220 plus a
bottom strip at rotation 3). The cyan focus stays distinct from the green state colour, and state is carried in words as
well as colour.

Standards used as the finding references (short tags in the table):

| Tag | Meaning |
|---|---|
| ISA-L1 / ISA-L2 | ISA-101 glanceable overview versus detail display |
| IEC-RC | IEC 60073 redundant coding: colour never alone, always plus word or shape |
| H1..H10 | Nielsen heuristics (H1 status, H3 control and exit, H4 consistency, H6 recognition, H8 minimal) |
| HICK, MILLER, FITTS, PRAG, VON-R | Hick, Miller, Fitts, Pragnanz (simplicity), Von Restorff (one standout) |
| EXC | Cooper excise (cognitive, visual, navigational) |
| UXW | UI_DESIGN.md section 6 copy rules (short, a verb, no jargon) |
| K2-nn | k2-micro-gui settled decision (flagged where a screen deviates) |

## 3. Proposal per screen

Widget mapping uses the existing names: `MenuList` (24 px / 39 px rows, rail 3 px, text x 26, right x 218), `ListView`
(scrolling list with rail), `Elem::paint` (signature-gated paint), `Field` (one value, repaints on change),
`draw_footer(_cached)` (band y 222..239), `setup::put_heading`, `draw_pill`, `fill_round`, `IconCell`.

### 3.1 Charger Results (F1): restore the grid

Before `docs/ui_review_2026-11-06/b_ct_results.png`, after `a_ct_results.png`.

- Counters become words plus colour: `16 pass` (green), `4 fail` (red), `3 skip` (grey), 24 px digits with 12 px words, one
  row, no card. Counter widget: three `Field`s (new, thin) in one `Elem`.
- A one-line legend (`check pass`, `cross fail`, `dash skip`, `volts`) at 12 px: shape plus word plus colour (IEC-RC).
- One row per unit, 24 px pitch (same as `MenuList::kRowH1`), unit name left, a cell per voltage right: a 29x20 tinted cell
  with a shape (check, cross, dash) and the voltage. Wide rows that have no voltages (SPR AVS "not offered") print words.
- The focused row gets the cyan rail and `kFocusT` tint exactly like `MenuList`; the footer explains the focused unit
  (`QC2 9V: no response in 2.0 s`, error icon, error colour); OK opens Steps, long OK keeps its meaning.
- Scrolling: `ListView` with the existing 3 px rail; six rows visible at 240x220.
- Mapping: new `ResultGrid` painter on `ListView`'s row callback; the cell painter is the only new primitive. Not a new
  page: `Stage::Results` of `ChargerTestPage`.
- Deviation flag: none. This restores the settled grid decision (K2 grid), see F1.

### 3.2 Shared wizard header (F3, F5, F2): one compact header

Before `b_ct_algorithms.png`, `b_ct_review.png`; after `a_ct_algorithms.png`, `a_ct_review.png`.

- Header band, 44 px: left `n/N` in 12 px dim, then the title in 16 px, then a 6-segment progress bar on the right
  (done = silver, current = white, todo = rule colour). Replaces the heading card on the charger wizard and aligns the FC
  and PD trigger headers to the same band.
- The body list is a normal `MenuList`/`ListView`: rows 24 px, state as a word in a tinted pill (`ON`, `OFF`, `SKIP`),
  the green pill for state, the cyan row for focus: they never swap.
- "Next: Cable / Spoof" stays the first (focus) row so the progression is the default action.
- Review: key/value rows in 16 px (Tests, Peak, Cap, Header, Spoof), the single action as a full-width focus row (`START
  tests` with an amber `OK x2` pill), the hint line "Voltage only; no load test", the amber footer
  "No load! OK twice within 5 s" with the warning icon.
- Mapping: `setup::put_heading` gets a second form (`put_wizard_header(step, of, title)`); the card code goes. The footer
  band is unchanged. Rows reuse `MenuList::draw_row`.
- Deviation flag: removes the charger heading card. Check with the user; it is not in the k2-micro-gui settled list but it
  is what the charger flow looks like today.

## 4. Strip vocabulary (F2)

Rule: the slot name is the verb of the short press; the long press (global page switch) is always the same word.

| Slot | Short press label | Long press label | Today (variants seen) |
|---|---|---|---|
| [-] (list pages) | `Up` | `Prev` | `Up`, `Up/Prev`, `-/Prev`, blank |
| [-] (value pages: Home, Diag, Lines) | `-` | `Prev` | `-/Prev` (dim on the first page) |
| [+] (list pages) | `Dn` | `Next` | `Down`, `Dn/Next` |
| [+] (value pages) | `+` | `Next` | `+/Next` |
| OK | a verb for the focused item: `Open`, `Start`, `View`, `Toggle`, `Pick`, `Span` | page-specific (`Reset` on Home) | `Next`, `Start`, `Open`, `Pick`, `Span`, `View`, `Steps` |
| BACK | `Back` always; `Exit` on step 1 of a wizard (state in words) | none (hold 5 s reboots) | `Back`, `Prev`, `Cancel`, `Back/Del` |

- In wizards OK reads `Next` (`Start` on the last step) and BACK reads `Back`; `Prev` is reserved for the long-press page
  action, so it no longer means two things.
- The footer band carries state or a hint (`13/13 ON; the rest SKIP`, `Load attached: unplug it`), never the strip text.
- The strip lengths (66/54/54/66 px at 6 px per character) give about 10 characters in the outer slots and 8 in the
  inner slots (divider and padding included); `Dn/Next` (7) and `Up/Prev` (7) fit the 54 px slots, `Toggle` (6) fits.

## 5. Implementation plan

One mergeable step each; every step keeps `make gate` green. Budgets are from `tests/test_ui_perf.cpp` (host-measured
streamed pixels); a changed screen re-baselines its `test_ui_capture` entries (760 pixel-exact checks today).

| Step | Change | Files | Tests and budgets |
|---|---|---|---|
| 1 | Tools readiness tag on every non-Ready row (3.3) | `src/ui/ui_pages.cpp` (`ToolsPage::row_fn`) | `tools move` stays <= 26 000 px; tag pill adds < 600 px per full paint; capture re-baseline for `tools*` |
| 2 | Text-only fixes (3.5): Lines, Diag overflow, USB link, Cards, PD tab, naming | `src/ui/ui_pages.cpp`, `include/k2/ui/ui_labels.hpp` | capture re-baseline for the touched screens; no new px budget (same glyph counts); add a `fit_text` test for the middle-truncation |
| 3 | Strip vocabulary (section 4) | `src/ui/ui_labels.cpp`, `src/ui/ui_pages.cpp` (`labels()` per page), `src/ui/ui_charger_test.cpp` | `tests/test_ui_labels.cpp` table test, strip strings only, 0 px change in budgets; footer hint strings in the capture checks |
| 4 | Shared wizard header (3.2) on the charger wizard first, then FC and PD triggers | `include/k2/ui/ui_setup_page.hpp`, `src/ui/ui_charger_test.cpp`, `src/ui/ui_pages.cpp` | `ct scroll` budget 24 000 px stays (the header is fixed, the list is smaller, so row paints are cheaper); page switch to Charger must not exceed today's number; review and algorithms captures re-baselined |
| 5 | Results grid (3.1) | `src/ui/ui_charger_test.cpp` (`Stage::Results`), new cell painter | new budget: a selection move repaints two rows (2 x 224 x 24 = 10.8 k px) + footer (4 k px), target <= 16 000 px; first paint of Results <= 60 000 px; extend `test_result_layout` for the 24 px pitch and the cell widths (6 rows visible at 220 px) |
| 6 | Home idle and flat labels (3.4) | `src/ui/ui_pages.cpp` (`draw_strips`, `draw_rows`) | steady idle tick must stay < 6 000 px per 100 ms (should drop: no label redraw); `home` page switch <= current budget; capture re-baseline for the idle and flat Home states |

Order rationale: steps 1 to 3 are cheap and independent; step 4 unlocks 5 (shared header and list height); step 6 is last
because Home is the walk-by screen and gets the least churn.

Step 5 as built (branch `k2/ui-charger-flow`): 18 px rows (eight visible), cells show shape plus volts plus amps, counters
as words with their shapes (the legend), one summary strip. Measured budgets differ from the plan where the ListView
forces it: a selection move that stays in the window is 12 to 16.2 k px (budget 17 000), a move that scrolls repaints
eight rows, about 53 k px (budget 56 000, no blit in ListView); the first paint is about 80 k px (budget 82 000; one pass
over the body is 50 k, the rest is the opaque row base under the chips and the header bands that repaint over the wipe).
Amps are the PDO's advertised current for PD, the probed current for a Mi hunt; legacy D+/D- modes have no current in the
data model and show volts only.

## 6. Open questions for the user

1. Results cell design: tinted cells with shape plus voltage (as mocked), or a bar of shapes only (denser, more rows)?
2. The charger heading card: remove it everywhere (as proposed) or keep it only on Review and Results as a summary card?
3. Per-tool readiness predicates: which tools should show `LOAD` versus `INLINE`? The mock uses today's `tool_readiness`.
4. Strip vocabulary: accept `Up/Dn` for lists and `-/+` for value pages, or one pair for both?
5. Home flat range: one centred label (proposed), or no label at all while the range is flat?
6. BACK on step 1 of a wizard: `Exit` (proposed, states the consequence) or keep `Back`?
7. Diag overflow: keep amber for very large counters, or show them neutral (the "4294M" case is a layout fixture)?

### 6.1 Answers (user, 2026-11-06)

1. Results cells: denser than the mock (more rows visible), and every cell keeps the current: volts AND amps, not volts
   alone.
2. Heading card: keep a summary card, but only for what matters: the highest-wattage passing mode per protocol family
   (examples: `PD 20V 3A`, `Mi 6A 20V 6A`). The step-counter card on the other setup pages goes (compact header, 3.2).
3. LOAD versus INLINE: decided per tool by what the tool does (a tool that draws or asks for power is hurt by a load; a tool
   that talks to the source only is hurt by a sink inline). Each tool owns its predicate; no shared guess.
   Resulting table (implemented in `src/ui/ui_tools.cpp`, one predicate per tool plus `tool_hurt_by()`; pinned by
   `test_hurt_table` in `tests/test_ui_tools.cpp`). "Far port occupied" is the single fact `SetupState::inline_mode`;
   what it means depends on the tool:

   | Tool | Hurt by | Tag when the far port is occupied | Level | Why |
   |---|---|---|---|---|
   | FC trigger | load | `LOAD` | blocked | handshakes a new voltage on D+/D-; a sink downstream would take it |
   | E-marker | inline | `INLINE` | caution | queries the cable; a device downstream hides the far end, so it only listens (`SRC ON` when a charger drives VBUS) |
   | Identify | inline | `INLINE` | caution | asks the partner device; with the far port occupied the question reaches the charger (OK twice forces it). Was `LOAD`. |
   | PD trigger | load | `LOAD` | blocked | requests a contract; a load downstream would take it (also `NO PD` without a source) |
   | Cable R | nothing | none (`NO PM` without the meter) | ready | measures under the user's own load; a load is the intended state |
   | Black Box | nothing | none | ready | passive recorder |
   | Spoof | load | `LOAD` | blocked | answers as a cable with Auto-CRC off; a live sink downstream would be cut |
   | Report cards | nothing | none | ready | read-only |

   The charger test is not a Tools row; it keeps its own refusal ("no load", voltage only) in its flow.

4. Strip vocabulary: accepted (`Up/Dn` on lists, `-/+` on value pages).
5. Home idle/flat: grey zeros instead of `--` or missing numbers, and `waiting for VBUS` written over one of the strips.
6. BACK on wizard step 1: keep `Back` (it exits; no `Exit` label).
7. Diag overflow: neutral colour, not amber.

Side issues (section 7): all three are to be fixed, not left.

## 7. Coverage and limits

Rendered as-is (before): Home (live, idle, flat, stale, error, no VBUS, reverse), Detail, PD (source, cable, sink, EPR,
no caps), Diag (normal, huge, no meter), Lines (empty, DCP, QC, AI), Tools hub and rows, Settings, USB link,
Cards (list, detail, confirm), Black Box (list, live, link), Spoof, E-marker, Identify, Match, FC and PD trigger wizards,
Cable R, and the charger flow (algorithms, cable, review, identity dialog, confirm, running, results, steps, detail) at
rotations 0, 90, 180 and 270 where captured.

Limits, stated plainly:
- After-mocks are drawn at rotation 3 (240x220 content). They use only the 224-wide logical viewport, so the other
  rotations reflow through `ContentViewport`, but they were not re-rendered rotated. Re-render at implementation time.
- Mock data is illustrative (voltages, counts). The mocks are overlays on host-rendered screens, not a running prototype.
- The strip vocabulary is a table, not a render. Home flat is described, not drawn.
- No hardware was used; nothing here is hardware-verified.

Side issues noticed (left unfixed):
- The incremental repaint of Charger Results leaves stale chip fragments in the host render (a forced repaint is clean).
  Not reproducible on main (fixed by ae27c95); the Results grid rewrite keeps a per-scroll forced-repaint diff test.
- `tests/test_ui_capture.cpp` charger navigation was stale (OK on Review opened the Cable identity dialog, so "ct_results"
  showed Review). Fixed on main; the dialog is gone since the Cable step carries the one identity list.
- Footer severity-icon use is inconsistent across pages (F10 is one case).
